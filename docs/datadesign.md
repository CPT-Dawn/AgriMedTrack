The architecture of the Firestore database is the most critical component for the application's success, directly influencing performance, scalability, and the ability to deliver the complex features required. The design employs advanced NoSQL data modeling patterns to optimize for the application's specific read-and-write patterns.  

2.1. Data Modeling Strategy: Denormalization and Hierarchy
The core strategy is a deliberate shift from traditional relational database normalization. It prioritizes fast read operations, which are frequent in the dashboard and sales forms, by strategically duplicating data. This approach results in more complex write operations, which are less frequent and can be managed by robust backend logic.  

Denormalization for Read Performance: To avoid complex and slow "JOIN"-like queries, data will be denormalized (duplicated) across collections. For instance, when a sale is recorded, the productName and supplierName will be copied into the sale document itself. This creates a self-contained, immutable record of the transaction. Without this, querying for a sales report would require fetching the main sale document, then fetching each product, and then each supplier, leading to slow performance and high read costs. This design ensures that the data required for a specific view, like a sales receipt or a dashboard summary, can be retrieved with a single, efficient query.  

Preservation of Historical Context: A significant benefit of this denormalization is the preservation of historical business data. For example, by storing the buyPrice and sellPrice within each sales record, the application can accurately calculate historical profit for any given transaction, regardless of future price changes for that product in the main inventory. This transforms the database from a simple state tracker into a reliable system for long-term business intelligence.

Hierarchical Data with Subcollections: For one-to-many relationships that have the potential for unbounded growth, such as the items within a single sale, subcollections are the ideal modeling choice. Storing an array of items directly in the parent  

sale document would be risky; as the number of items grows, the document could approach Firestore's 1 MB size limit, making it slow or impossible to load. By placing items_sold in a subcollection, the parent sale document remains small and easy to query, while the list of items can grow indefinitely without performance degradation.  

Separation of State and Logs: The user's requirement for separate inventory and inventory_logs collections is a sophisticated architectural choice that will be implemented.

The inventory collection represents the current, sellable state of the shop's stock. It is optimized for the fast queries needed during a sale (e.g., "how much of product X is available?").

The inventory_logs collection is an immutable, append-only ledger of all stock additions. It serves as an audit trail, tracking who added what, when, and at what cost. This separation dramatically simplifies the application logic: the "Add Sale" screen reads from inventory, while the "Inventory Log" screen reads from inventory_logs.

2.3. Data Flow & Business Logic (Cloud Functions)
To ensure data integrity and atomicity for critical, multi-step operations, the use of server-side Firebase Cloud Functions is mandated. Client-side operations are susceptible to partial failure due to network issues, which could lead to severe data inconsistencies (e.g., a sale being recorded but inventory not being decremented).

Logic 1: Adding New Inventory (onAddInventory Cloud Function)

Trigger: The function is invoked when the client submits the "Add Inventory" form.

Payload: It receives an array of new inventory items from the client.

Execution:
a. The function first creates a single, new document in the inventory_logs collection. This document contains the full payload, creating an immutable audit record of the transaction.
b. It then iterates through each item in the payload. For each item, it must find or create the corresponding document in the main inventory collection. This is a critical step that must be atomic.
c. Using a Firestore transaction, it queries the inventory collection for a document with the exact same productId, supplierId, packagingSize, and batchNumber.
d. If a matching document exists: The function performs an atomic increment on the quantity field of the existing document.
e. If no match is found: The function creates a new document in the inventory collection with the details from the payload.
f. The transaction ensures that both the logging and the inventory update succeed or fail together, preventing any data discrepancies.

Logic 2: Processing a Sale (onProcessSale Cloud Function)

Trigger: The function is invoked when the client submits the "Add Sale" form.

Payload: It receives the complete sale object, including customer details and an array of items being sold.

Execution (within a single Firestore transaction):
a. Stock Verification: The function first iterates through each item in the sale. For each one, it reads the corresponding document from the inventory collection and verifies that the available quantity is greater than or equal to the quantitySold. If any item has insufficient stock, the entire transaction is aborted, and an error is returned to the client. This prevents overselling.
b. Stock Decrement: If all items have sufficient stock, the function performs an atomic decrement on the quantity field for each corresponding inventory document.
c. Sale Record Creation: A new document is created in the sales collection with the summary information.
d. Line Item Creation: The function then iterates through the sale items again, creating a new document for each one in the sales/{sale_id}/items_sold subcollection. These documents contain the fully denormalized, point-in-time data.
e. Customer Record Update: The function reads the relevant customers document. If the sale is not fully paid (amountPending > 0), it atomically updates the totalPendingAmount and adds the new saleId and its pending amount to the pendingSales map. If the customer does not exist, a new customer document is created.
f. The transaction is committed. This guarantees that stock is updated, the sale is recorded, and customer balances are adjusted as a single, indivisible operation.

Part 3: Application Modules & Screen Specifications
This section provides a detailed blueprint for each screen in the application, outlining the user interface, component structure, and client-side logic.

3.1. Authentication Flow
The authentication flow is the entry point to the application, secured by Firebase Authentication.

Screen: Login (LoginScreen.js)

UI Layout: The screen will feature a clean, centered layout to focus the user on the login task.

An application logo will be displayed prominently at the top.

Below the logo, the store name "Patel Krishi Kendra" will be rendered in a large, styled font.

A Card component from react-native-paper will contain the login form.

The form will consist of two TextInput components (from Paper) for "Email Address" and "Password", complete with labels and placeholder text.

A primary Button (from Paper), styled with the theme's primary color, will be labeled "Login".

An ActivityIndicator (from Paper) will be displayed overlaid on the button or next to it while the login request is in progress.

Logic:

The component will use state to manage the email and password inputs.

Form validation will be implemented to check for a valid email format and non-empty password before attempting to sign in.

The "Login" button's onPress handler will call Firebase Authentication's signInWithEmailAndPassword method.

Upon successful authentication, the application will navigate to the main app stack, landing on the Dashboard screen.

Any errors returned from Firebase (e.g., wrong password, user not found) will be caught and displayed to the user via a Snackbar component from Paper, providing clear feedback.

Animation: react-native-reanimated's Layout animation will be applied to the main container. This will cause the logo and form card to gracefully fade and slide into view when the screen first loads, providing a polished entry experience.

3.2. Core Navigation
The application's navigation is designed for simplicity and intuitive access to the main functional areas.

Bottom Tab Navigator:

The primary navigation will be a bottom tab bar, implemented using @react-navigation/bottom-tabs.

It will feature three main tabs, each with an icon and a label:

Dashboard (Icon: e.g., home-outline)

Sales (Icon: e.g., cart-outline)

Inventory (Icon: e.g., archive-outline)

Icons will be sourced from react-native-vector-icons. The active tab's icon and label will be colored with the theme's primary color to provide clear visual indication of the current screen.

Header Bubbles for Sub-page Navigation:

To fulfill the requirement for a simple navigation structure that avoids complex menus, a custom header component will be created. On screens that have related sub-pages (like InventoryListScreen and SalesListScreen), this header will display small, tappable "bubbles".

These bubbles will be implemented using the Chip component from react-native-paper.

Example: On the InventoryListScreen, the header will contain two chips: "Add Stock" and "View Logs". Tapping "Add Stock" navigates to the AddInventoryScreen, and tapping "View Logs" navigates to the InventoryLogScreen. This pattern keeps the main screen uncluttered while providing quick access to related actions.

3.3. Dashboard Module (DashboardScreen.js)
The dashboard is the central hub for at-a-glance business insights. It must be dynamic and responsive, reflecting data changes in real-time.

Component Breakdown:

Greeting Header: The top of the screen will display a personalized greeting, "Good Morning,". The user's name will be fetched from the users collection based on the currently authenticated user's UID. This header will also contain an icon button for "Logout", which will trigger the Firebase signOut method and navigate the user back to the LoginScreen.

Statistics Cards Grid: A 2x2 grid will display four key performance indicators, each within its own Card component for visual separation.

Total Sales: Displays the lifetime total sales value, formatted as currency.

Total Profit: Displays the lifetime total profit, formatted as currency.

Pending Collections: Shows the total outstanding amount to be collected from all customers.

Inventory Value: Displays the total current value of all stock on hand, calculated as the sum of (buyPrice \* quantity) for all items in the inventory collection.

Pending Payments Section: A List.Section from Paper, titled "Customers with Pending Payments".

This section will display a scrollable list of customers who have an outstanding balance (totalPendingAmount > 0).

Each entry will be a List.Item, showing the customer's name on the left and their total pending amount on the right.

Tapping on a customer will navigate to a detailed view showing the specific sales that have pending payments.

Recent Activity Section: This section will use a SegmentedButtons component from Paper to allow the user to switch between two lists.

Recent Sales: When selected, this shows a list of the 5 most recent sales transactions, ordered by saleDate.

Recent Stock Additions: When selected, this shows a list of the 5 most recent inventory logs, ordered by addedAt.

Firestore Queries & Logic:

To ensure the dashboard is always up-to-date, it will use onSnapshot real-time listeners from @react-native-firebase/firestore for all its data sources.  

A key performance optimization will be implemented for the main statistics. Instead of the client app calculating these totals (which would be inefficient for large datasets), a dedicated Cloud Function will be triggered on every new sale or inventory change. This function will perform the aggregation and update a single document, for example stats/summary. The dashboard will then only need to listen for changes to this single document, making it extremely fast and efficient.  

Animation:

react-native-reanimated's Layout animations will be applied to the "Pending Payments" and "Recent Activity" lists. When a new item appears (e.g., a new sale is made), it will animate smoothly into the list instead of just appearing abruptly.

When the values in the statistics cards update, a "count-up" animation will be triggered, providing a dynamic visual cue that the data has changed.

3.4. Inventory Module
This module is the heart of the shop's management functionality, covering stock viewing, addition, and logging.

Screen: Inventory List (InventoryListScreen.js)

UI Layout:

A Searchbar component from Paper will be fixed at the top, allowing users to filter the list by productName, supplierName, or batchNumber.

The main content area will be a FlatList rendering custom ProductCard components.

Each ProductCard will represent a unique item from the inventory collection and display essential information: productName, supplierName, batchNumber, packagingSize, and the current quantity.

Each card will feature a color-coded Chip to indicate the stock level (e.g., red for quantity < 10, orange for quantity < 50, green for higher quantities), providing quick visual cues.

Logic: The screen will fetch and display all documents from the inventory collection. The search functionality will be implemented client-side, filtering the displayed list based on the text input in the search bar.

Screen: Add Inventory (AddInventoryScreen.js)

UI Layout: This screen implements the requested dynamic form for adding multiple products in a single transaction.

The screen will initialize with a single form group for one inventory item.

Each form group will contain a set of inputs: dropdowns for Product and Supplier, text inputs for Packaging Size (split into number and unit), Batch No., Quantity, Buy Price, and Sell Price, and date pickers for MFD and Expiry Date.

A prominent "Add Another Product" button will be at the bottom. Tapping it will dynamically append a new, identical form group to the screen, allowing for batch entries.  

Each dynamically added form group will have a "Remove" icon button to delete it from the form.

Logic: The "Add-to-Dropdown" Feature: This is a critical user experience feature.

The "Product" and "Supplier" dropdowns will be implemented using react-native-element-dropdown.

The dropdown component will be configured to render a custom footer component. This footer will contain a TextInput and an "Add" button.

User Flow: A user starts typing a product name that doesn't exist (e.g., "NewBrand Fertilizer"). They type it into the dropdown's footer input and tap "Add". This action triggers a call to a Cloud Function that creates a new document in the products collection. Upon successful creation, the client-side list of products is refreshed from Firestore, the new product now appears in the dropdown list, and it is automatically selected. This seamless flow prevents the user from having to leave the form to add a new master data entry.

Logic: Packaging Size Input: As specified, the UI will present two separate inputs for packaging: a numeric TextInput for "Size" and a text TextInput for "Unit" (e.g., "kg", "litre", "ml"). On form submission, the backend logic will combine these into the packagingSize string (e.g., "50 kg") while also storing the raw packagingSizeValue (50) and packagingUnit ("kg") for potential future calculations or filtering.

Screen: Inventory Log (InventoryLogScreen.js)

UI Layout: This screen will display a chronological, immutable history of all stock additions.

It will be a FlatList of Card components.

Each card will represent a single document from the inventory_logs collection.

The card will display who added the stock (addedByName), when it was added (addedAt), and a nested list of all the items included in that specific transaction, showing product name, quantity, and batch number.

3.5. Sales Module
This module handles the entire sales process, from creating a new sale to viewing past transactions.

Screen: Sales List (SalesListScreen.js)

UI Layout:

The screen will display a list of Card components, with each card representing a single document from the sales collection.

Each card will show key sale information: customerName, billNumber, saleDate, and totalAmount.

A prominent Chip component will display the paymentStatus ("Paid", "Unpaid", "Partial") and will be color-coded for immediate recognition (e.g., green for Paid, red for Unpaid, orange for Partial).

Each card will have "Edit" and "Delete" icon buttons to allow for modification or cancellation of a sale (with appropriate confirmation dialogs).

Screen: Add Sale (AddSaleScreen.js)

UI Layout: A comprehensive form for creating a new sales transaction.

The top of the form will have inputs for customer information (Name and Phone Number).

Below this will be a dynamic list for adding the items being sold, similar in structure to the "Add Inventory" screen.

Logic: Cascading Dropdowns: This is the most complex UI interaction in the application and must be implemented precisely to ensure a smooth user experience. The logic will follow established patterns for dependent dropdowns.  

Step 1: Select Product: The user first selects a product from a dropdown. This dropdown is populated with the unique productNames of all items currently available in the inventory collection (i.e., where quantity > 0).

Step 2: Select Supplier: Once a product is selected, the component triggers a Firestore query: firestore().collection('inventory').where('productId', '==', selectedProductId).where('quantity', '>', 0).get(). The unique supplierNames from the query results are used to populate the second dropdown. This dropdown remains disabled until a product is selected.

Step 3: Select Packaging Size: Once a supplier is selected, the available packagingSize options for that specific product-supplier combination are filtered from the previous query results and used to populate the third dropdown.

Step 4: Select Batch Number: Finally, once the packaging size is chosen, the available batchNumbers for that specific product-supplier-packaging combination are populated in the fourth dropdown.

Real-time Stock Feedback: Crucially, next to the quantity input for the item, a Text component will dynamically display "Stock available: [X]", where [X] is the quantity from the final, fully specified inventory item selected through the cascading dropdowns. This provides immediate, essential feedback to the user, preventing attempts to sell more stock than is available.

Logic: Bill Calculation: As the user adds items and specifies quantities, the total bill amount, including any taxes or discounts, will be calculated and displayed in real-time at the bottom of the screen, providing a running total.

Part 4: Component Library & Animation System
This section defines the application's reusable visual elements and the overarching strategy for animation, ensuring a consistent, polished, and high-quality user experience.

4.1. Reusable Component Specifications
To promote DRY (Don't Repeat Yourself) principles and ensure visual consistency, the following components will be created in the /src/components directory.

ProductCard.js: A self-contained Card component that accepts an inventory item object as a prop. It will be responsible for rendering the product name, supplier, batch, quantity, and the color-coded stock level indicator. This component will be used in the InventoryListScreen.

PrimaryButton.js: A wrapper around react-native-paper's Button component. It will be pre-styled with the theme's primary color, standard padding, and typography to ensure all primary call-to-action buttons look identical.

DataInput.js: A wrapper around react-native-paper's TextInput. It will encapsulate standard styling, validation logic, and error message display, simplifying form creation.

CascadingSaleItemForm.js: This will be a complex, self-contained component that encapsulates the entire cascading dropdown logic for a single line item in a sale. By isolating this logic, the AddSaleScreen's code will be significantly cleaner and easier to manage.

AnimatedModal.js: A reusable modal component that uses react-native-reanimated to animate its entry and exit (e.g., sliding up from the bottom or fading in with a scale effect), providing a more polished experience than a standard modal.

4.2. Animation Strategy
Animations will be used purposefully to enhance the user experience, not merely for decoration. The goal is to use motion to provide feedback, guide user attention, and create a sense of fluidity and responsiveness, in line with modern UX principles.  

Layout Animations: The Layout animation feature from react-native-reanimated will be applied to all lists where items can be dynamically added or removed. This includes the inventory list, sales list, and the dynamic forms on the "Add Inventory" and "Add Sale" screens. When a new item is added, it will gracefully fade and slide into place. When removed, it will animate out. This provides clear visual confirmation of the user's action.

Micro-interactions: Subtle animations will be used to make the UI feel more responsive and tactile.

Buttons will have a "scale down" effect on press, implemented with useAnimatedStyle and a withSpring animation from react-native-reanimated. This provides immediate physical feedback that the touch was registered.

Tapping on cards in a list will trigger a subtle visual effect, such as a gentle "lift" (by animating the shadow) or a brief highlight, confirming the selection.

High-Impact Feedback with Lottie: The lottie-react-native library will be used for more complex, branded animations at key moments.

Success Animation: After a user successfully completes a major action like submitting a large inventory order or finalizing a sale, a full-screen modal will briefly appear, displaying a custom Lottie animation of a spinning checkmark. This provides a moment of positive reinforcement and clear confirmation that the complex operation was successful.

Loading Animation: For longer data-loading operations, a custom Lottie animation (more visually engaging than a standard spinner) can be used to maintain user engagement and reinforce the app's brand identity.

The animation strategy transforms the "animation-full" requirement from a potential source of clutter into a core element of the app's communication system. By using motion to confirm actions, guide focus, and smooth transitions, the application will feel both powerful and simple to use.
